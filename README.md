# 跨区域水资源使用权分配与转让

一个仅使用 Python 标准库实现的水权账户、计量、转让审批、旱期限额令和干旱情景服务。SQLite 保存账户额度、取水记录、限额令、季节规则、上下游影响规则、计量收件箱、对账记录和完整审计日志。

## 运行

```bash
python app.py --init
python app.py --port 8007
```

打开 <http://127.0.0.1:8007>。`--init` 会创建北区水库和河口灌区两个示例账户，并添加一条 7 月季节上限和一条最小留存规则。数据库默认是 `water_rights.db`，可用 `--db` 或 `WATER_DB` 修改。

服务启动时会先执行 `recover_pending()`：把崩溃前已接收但未入账的计量事件继续处理完（见“崩溃恢复”）。

## 角色

请求头 `X-User` 和 `X-Role` 模拟身份：

- `editor`：配额管理员/水权编辑，建账户、设规则、发起转让。
- `reviewer`：审核人，批准/退回转让。
- `meter`：计量员，登记取水。
- `dispatcher`：**旱情调度员**，发布/更新旱期限额令。
- `viewer`：只读。

## API

- `POST /api/accounts`：建立账户（额度、优先级、有效期）。
- `POST /api/rules/season`：设置某地区某月份的用水比例上限。
- `POST /api/rules/impact`：设置上下游转让的最小留存比例。
- `POST /api/drought/orders`：发布或更新旱期限额令（`region`、`effective_from`、`cap_fraction`、`note`）。
- `GET  /api/drought/orders`：限额令列表。
- `POST /api/transfers`：发起转让；待审批金额立即预占，避免同一额度被重复转卖。
- `POST /api/transfers/{id}/approve|reject`：审核；发起人不能审批自己的记录。
- `POST /api/usage`：按计量事件登记实际取水，同一账户同一事件编号只会入账一次。可带 `transfer_id` 关联转让做对账。
- `GET  /api/accounts/{id}/available?as_of=YYYY-MM-DD`：查看某日生效限额、扣减实际用量和待审批预占后的可用额度。
- `GET  /api/reconciliation`：转让-计量对账报告（匹配差异、待对账双方、未入账事件）。
- `GET  /api/drought/simulate?supply=1000&reduction=0.3`：按高优先级先行分配，同级账户按剩余额度比例分配。
- `GET  /api/audit`：完整操作审计。

写接口支持 `Idempotency-Key` 请求头：同一键的重复提交返回首次结果，不会重复创建或重复扣减；同一键换载荷返回 409。

## 旱期限额令如何接入账户、取水和转让

- 限额令按 `(region, effective_from)` 生效，同一地区同日唯一；更新只改比例并重新执行约束。某日的有效限额为该地区生效日不晚于该日的最新一条。
- 账户有效额度 `limit = min(许可额度 quota, quota × cap_fraction)`；`available = limit − used − 待审批预占`，不为负。
- **限额令发布/更新后**，对受影响地区的每个账户重算可用量（审计 `account.availability_recomputed`）。
- **超限的待审批转让自动退回**：按“先到先得”保留能放下且满足下游最小留存的转让，其余标记 `rejected` 并记录退回原因（审计 `transfer.auto_rejected`）。
- **已登记取水不回改**：限额收紧只影响之后的取水、转让与待审批预占；历史取水行和 `used` 保持不变，因此限额低于已用量时可用量显示为 0。
- 限额下登记取水按取水日期适用当时的限额；季节配额也以限额后的额度为基数。
- 批准转让时按转让生效日当前限额重新复核，限额收紧后放不下的转让不能批准。
- 最小留存比例始终按原始许可额度 `quota` 计算，限额令只会让约束更紧。

## 并发占用

余额判断与写入都在单条 SQLite 事务中以 `BEGIN IMMEDIATE` 串行执行（`busy_timeout=10s`）。多人同时提交取水或转让时，同一份额只能被一方占用：先拿到写锁的事务成功，其余事务按更新后的余额判定为超额并被拒绝。

## 崩溃恢复与不重复扣减

计量处理分两个独立提交阶段，状态持久化在 `meter_inbox`：

1. **接收**：校验通过后把事件原子写入收件箱并提交。若服务随后崩溃，重启时 `recover_pending()` 会继续。
2. **入账**：插入 `usage_records`、增加 `used`、写 `posted_at` 标记，同一事务提交。
   - 入账前崩溃：重启后看到 `posted_at` 为空，重新入账。
   - 入账提交后、标记前崩溃：`(account_id, meter_event_id)` 唯一约束会让重插入冲突，此时跳过 `used` 增量，只补标记——绝不重复扣减。
3. **对账**：关联转让的事件再写 `reconciled_at`，批准转让时也会补做对账，因此计量早到、晚到都能收敛。

各阶段都以自己的提交标记为准，重复执行恢复是无操作的。

- 校验失败（超额/季节等）的事件会保留在收件箱并记录 `error`，不会入账；之后可用**同一事件号按修正后的载荷重试**，成功后只保留一条入账记录。
- 已入账的事件再次提交返回“不能重复计水”。

## 晚到计量对账

带 `transfer_id` 的计量事件以“实际到水量”入账到受让方，并与已批准转让的批准量对账：

- 计量晚到：入账后立即按该转让**聚合所有**关联计量事件，差异 = 实到合计 − 批准量，状态 `matched` / `short`（损耗欠量）/ `over`（超量）。
- 计量早于批准：先入账并挂起，批准时在同一事务补对账。
- **两边记录都保留**：批准的转让行不改动，计量事件留在收件箱和取水账中，只新增/更新 `transfer_reconciliation` 差异汇总；差异写入审计 `reconciliation.mismatch`。
- `GET /api/reconciliation` 返回：差异明细、等待转让批准的计量、已批准但尚无计量的转让、未入账事件。

## 测试

```bash
python -m unittest discover -s tests -v
```

测试覆盖：限额令重算可用量、FIFO 自动退回超限待审批、已登记取水不回改、限额下取水/转让拦截、限额下保留转让的批准；取水与转让的并发只一方成功；崩溃恢复入账一次、重复恢复不二次扣减、幂等键重放；晚到/早到计量的匹配、欠量、超量对账；以及既有的转让审批与计量、重复计量事件、季节/最小留存规则、发起人自审冲突。
